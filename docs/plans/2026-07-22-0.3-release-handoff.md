# AME 0.3 release handoff tasks

This is the execution checklist for closing the 0.3 agent-first learning loop
on the current branch. The 0.3 product scope is defined by
[`docs/ROADMAP.md`](../ROADMAP.md) and the six certification stories in the
[agent-first rework plan](2026-07-19-agent-first-learning-rework.md).

The July 20 audit reports C1-C6 as passing. These tasks refresh the evidence on
the current HEAD and make the handoff decision explicit; they do not reopen the
already-settled 0.3 product scope.

## Execution rules

- Run commands from the repository root through the Makefile or the documented
  repository scripts.
- Use an isolated `ame-clean` compose project for destructive clean-volume
  rehearsal. Never remove the normal local `ame` volumes.
- Record exact commands, observed results, and limitations in an audit file.
- Do not add reviewer UI, reviewer decision endpoints, agent accounts, sharing,
  or other explicitly deferred features to the 0.3 release.

## Immediate 0.3 certification tasks (not publication)

### R0 — Freeze the handoff scope

- [x] Confirm the current branch and clean Git status.
- [x] Confirm the authoritative roadmap and current release inventory.
- [x] Confirm the existing four stale worktree records are removed.
- [x] Record the final release candidate commit in the handoff audit.

Acceptance: the handoff names one commit and does not mix the superseded July 1
rebrand plan into the 0.3 release gate.

### R1 — Run the repository quality gate

- [x] Run `make check` on the release candidate.
- [x] Run `make test-api` against the isolated Caddy stack.
- [x] Verify formatting and SQL lint output has no actionable failure.
- [x] Verify OpenAPI and generated frontend schema parity.
- [x] Record Rust and frontend test counts.

Acceptance: `make check` and the current-HEAD black-box API suite exit
successfully; warnings that do not fail the configured gate are recorded but do
not get presented as failures.

### R2 — Rehearse a clean isolated stack

- [x] Stop and remove only the disposable `ame-clean` compose project and its
  named volumes.
- [x] Start Postgres, Valkey, API, web, and containerized Caddy from the current
  source with a clean build.
- [x] Probe `/healthz`, `/readyz`, `/public/llms.txt`, `/public/skill.json`, and
  `/public/openapi.yaml` through the Caddy origin.
- [x] Confirm static public documents are served by Caddy and `/public/v1/*`
  remains API-backed.

Acceptance: all required services become ready and all five public probes return
HTTP 200 from the single Caddy origin.

The Podman machine required starting and using the isolated compose project in
one command session. The normal `ame` project was briefly started during
diagnosis, then stopped without removing its volumes. No normal volumes were
deleted.

### R3 — Certify the learner loop through the real origin

- [x] Register and log in a fresh learner through `/public/v1`.
- [x] Start a prompt-grounded journey with an idempotency key.
- [x] Read the journey back and verify the raw intent, learner-owned goal,
  objectives, first activity, and recommendation.
- [x] Exercise the agent-authored assessment and deep-dive path.
- [x] Exercise manual-review assessment behavior and verify no false score or
  mastery progress is created.
- [x] Run the four focused browser journeys with `make local-uiux` against the
  isolated Caddy origin.

Acceptance: C1-C5 behavior is proven through HTTP/database assertions and the
browser gate passes all four journeys without a hardcoded-only shortcut.

### R4 — Verify persistence and restart/resume

- [x] Create a learner journey and durable progress on the isolated stack.
- [x] Restart the stack without deleting its volumes.
- [x] Log in again and read the same journey, progress, recommendation, and
  resume state.
- [x] Record the before/after identifiers and timestamps.

Acceptance: learner state survives a non-destructive restart on the same Caddy
origin; clean-volume and restart evidence are clearly distinguished.

### R5 — Assemble the release evidence bundle

- [x] Update `docs/audits/2026-07-22-0.3-release-candidate.md` with the candidate
  commit, commands, outputs, and C1-C6 pass/fail decisions.
- [x] Link the focused contract audits without duplicating their full content.
- [x] List bounded items: reviewer decision UI remains outside 0.3; no SMTP,
  hosted identity, sharing, or production code sandbox is included.
- [x] State whether the evidence is ready for internal implementation review.

Acceptance: an implementation reviewer can reproduce the certification evidence
from the audit and linked commands without treating it as a release approval.

### R6 — Optional local branch cleanup

- [ ] Confirm the four `worktree-agent-*` branches contain no unique work needed
  by the current branch.
- [ ] Delete only those obsolete local branches if explicitly approved after
  inspection.

Acceptance: no branch is deleted merely because its worktree was stale; branch
cleanup remains separate from release certification.

## 0.4 backlog after 0.3 handoff

These are candidates, not work to start before R2-R5 are complete. Each must get
its own kill-gate, contract, fixtures, tests, and local-stack/browser evidence.

1. Spaced retrieval and review scheduling.
2. Source import from URLs, documents, and local files.
3. Citation extraction, source snapshots, licensing, and grounding checks.
4. Learner notes and annotations.
5. Alternate explanations, harder variants, and additional examples.
6. Richer project submissions and rubric-based review.
7. Journey and learner-history export/import.
8. Better recovery options for deployments that configure identity services.
